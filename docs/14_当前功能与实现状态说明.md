# RepoSage 当前功能与实现状态说明

> 本文基于 2026 年 7 月 10 日当前代码整理，用于回答三个问题：RepoSage 现在能做什么、一次审查怎样运行、哪些 Agent/SCM/沙箱能力已经实现但尚未形成自动闭环。快速启动和环境变量见根目录 [`README.md`](../README.md)，系统全景与工程取舍见 [`00_项目详细介绍.md`](00_项目详细介绍.md)。

---

## 1. 当前项目定位

RepoSage 是一个面向 Git Commit 和 Pull Request Diff 的智能代码审查平台。

它已经能够完整运行以下经典链路：

```text
登录
→ 创建项目
→ 绑定 Git 仓库
→ 上传项目知识库
→ 选择 Commit 或手工登记 PR
→ 获取并分片 Diff
→ Mock 规则审查或真实大模型审查
→ 生成结构化报告
→ 人工确认、标记误报或提交 PR 决策
```

在经典审查平台之上，项目正在建设新的 PR 守门 Agent：通过 GitHub/GitLab webhook 创建持久化 AgentRun，在预算和状态机约束下调用仓库工具，并将结果发布回 PR/MR。

需要明确区分：

- **经典 Commit/手工 PR 审查链路已经可用。**
- **新 SCM webhook 入口、Agent 数据结构、sandbox-runner 和 publisher 等组件已经实现。**
- **Outbox 派发、Agent 步骤执行、后端到沙箱的真实调用和新 SCM 自动回写仍未贯通。**

## 2. 用户当前可以使用的功能

### 2.1 登录与鉴权

系统提供用户名密码登录、当前用户查询和退出登录：

```text
POST /api/auth/login
GET  /api/auth/me
POST /api/auth/logout
```

当前没有公开注册接口。只有同时显式配置以下环境变量时，`AuthSeedRunner` 才会创建种子账号：

```text
SEED_ADMIN_USERNAME
SEED_ADMIN_PASSWORD
```

两项应用默认值均为空；`deploy/.env.example` 和冒烟脚本中的账号仅是部署示例或脚本参数，不是应用默认账号。

登录后的接口支持 Bearer Token 和登录 Cookie。后端采用无状态 Spring Security 配置。

### 2.2 项目管理

用户可以：

- 创建项目；
- 查看项目列表和详情；
- 修改项目名称、描述和默认分支；
- 删除项目；
- 在项目维度隔离仓库、知识库、审查任务、报告和反馈。

删除项目时，后端会清理相关业务数据和本地仓库工作目录。

### 2.3 Git 仓库接入

项目可以绑定：

- GitHub；
- GitLab；
- Gitee；
- 其他 HTTP Git 地址；
- 本地 Git 仓库（开发配置允许）。

绑定后可以：

- clone 或 fetch 仓库；
- 查询 Commit 列表；
- 获取 Commit 的父提交；
- 生成 Commit 或 Base/Head 之间的 Diff；
- 在前端按文件展示新增行、删除行和 hunk。

Git 操作使用系统 `git` CLI，不使用 JGit。远程仓库 access token 使用 AES-GCM 加密后入库，读取接口不会返回明文 token。

### 2.4 项目知识库

每个项目可以上传 Markdown 或 TXT 文档，例如：

- 业务流程；
- 接口规范；
- 数据库结构；
- 历史 Bug；
- 安全规范；
- README；
- 编码约定。

上传后，系统按照 `RAG_CHUNK_SIZE` 和 `RAG_OVERLAP` 将文档切分成知识块，并按项目保存。用户还可以在前端输入自然语言问题，测试知识库召回结果和相似度。

### 2.5 审查任务与报告

用户可以：

- 指定 Commit、Base Commit 和分支发起审查；
- 不指定 Commit 时审查仓库最新提交；
- 选择参与审查的知识文档；
- 查看任务状态和错误信息；
- 停止仍在等待或运行中的任务；
- 删除任务及其报告、问题、反馈、AI/MQ 日志；
- 查看总体风险、问题列表、证据、影响和修改建议。

创建任务时会按项目、仓库、Head、Base 和分支进行幂等查找，并由数据库唯一约束处理并发重复创建。

### 2.6 人工反馈

每个审查问题支持三种反馈：

- `TRUE_POSITIVE`：真实问题；
- `FALSE_POSITIVE`：误报；
- `NEED_DISCUSSION`：需要讨论。

用户可以补充文字说明、更新自己的反馈或撤回反馈。当前反馈用于审查闭环和结果记录，尚未自动进入模型再训练流程。

## 3. 一次经典审查怎样运行

经典审查的核心入口是 `ReviewService` 和 `ReviewProcessor`。

```text
创建任务
→ 获取 Git Diff
→ 幂等保存 ReviewTask
→ inline 直接执行，或发布到 RabbitMQ
→ 可选轻量模型风险预判
→ 构建 RAG 上下文
→ DiffSplitter 按文件分片
→ Mock 或 OpenAI 兼容审查
→ 合并分片结果与 Token 用量
→ 保存 ReviewReport / ReviewIssue
→ 可选回写旧 GitHub PR 评论
```

### 3.1 同步与异步模式

开发环境默认：

```text
REVIEW_INLINE=true
```

任务会在当前后端进程中直接执行，不需要 RabbitMQ，适合本地开发和演示。

生产配置默认：

```text
REVIEW_INLINE=false
```

任务发布到 RabbitMQ，由 `ReviewTaskConsumer` 异步处理，避免长时间占用创建任务的 HTTP 请求。

### 3.2 轻量模型预判

启用以下配置后：

```text
MODEL_SERVICE_ENABLED=true
MODEL_SERVICE_URL=http://model-service:8000
```

后端会把 Diff 发送给独立 FastAPI 服务。模型服务使用：

- TF-IDF；
- Logistic Regression；
- joblib 模型文件。

当前分类主要覆盖：

- 权限风险；
- SQL 注入；
- 空指针；
- 业务规则风险；
- 事务风险；
- 性能风险。

轻量模型只是辅助信号，不负责生成最终报告。模型文件不存在或预测异常时，服务回退到规则判断；整个模型服务不可用时，Java 后端返回空信号并继续审查。

### 3.3 RAG 上下文构建

系统支持两种 RAG 使用方式。

#### 全量上下文

```text
RAG_FULL_CONTEXT=true
```

系统按文档和分片顺序把项目知识块直接拼入 Prompt，并受 `RAG_MAX_CONTEXT_CHARS` 限制。

适合：

- 知识库规模较小；
- 模型厂商只有 Chat API；
- 不希望依赖 embedding API；
- 希望完整注入业务规则。

#### 向量检索

```text
RAG_FULL_CONTEXT=false
RAG_MODE=memory
```

或者：

```text
RAG_MODE=pgvector
```

系统会：

1. 生成当前 Diff 的查询向量；
2. 计算查询向量与知识块向量的相似度；
3. 选取 Top-K 知识块；
4. 将来源、分片编号、相似度和内容拼入 Prompt。

`memory` 模式在 Java 内存中计算余弦相似度；`pgvector` 模式使用 PostgreSQL vector 距离查询。当前 pgvector 查询是基础的精确最近邻实现，尚未建立 HNSW/IVFFlat 近似索引。

默认 Mock embedding 使用本地确定性的 token-hash 向量，可以离线演示召回流程，但高质量语义召回仍需要真实 embedding 模型。

### 3.4 大 Diff 分片

当 Diff 超过单次模型调用预算时，`DiffSplitter` 会：

1. 按 `diff --git` 边界识别文件；
2. 按 `REVIEW_MAX_DIFF_CHARS` 将文件打包成多个分片；
3. 对每个分片分别调用审查客户端；
4. 合并问题列表；
5. 将总体风险取最高等级；
6. 累加各分片 Token 用量；
7. 合并摘要并记录跳过的文件数。

单个文件仍可能因为超过预算而被有提示地截断；超过 `REVIEW_MAX_FILES` 的文件不会审查，并会在最终摘要中说明。这样避免了把整个大 Diff 静默截断后漏掉后半部分文件。

### 3.5 Mock 规则审查

默认配置：

```text
AI_PROVIDER=mock
```

此时不会调用外部大模型，而是由 Java 关键词/模式规则直接生成结构化报告，主要用于：

- 无 API Key 的本地演示；
- 验证完整审查业务流程；
- 测试报告和反馈页面；
- 识别部分权限、SQL、空指针和业务规则风险。

当前规则属于演示级模式匹配，不是基于 AST、控制流或数据流的完整 SAST 引擎。

### 3.6 真实大模型审查

配置 OpenAI 兼容服务后：

```text
AI_PROVIDER=openai-compatible
LLM_BASE_URL=...
LLM_API_KEY=...
LLM_CHAT_MODEL=...
```

后端使用 Spring `RestClient` 调用兼容的 `/chat/completions` 接口，不依赖 Spring AI。Prompt 中包含：

- 当前 Diff；
- 可选轻量模型风险信号；
- RAG 项目上下文；
- 结构化 JSON 输出要求。

客户端提供：

- JSON 解析与字段归一化；
- 网络超时处理；
- Resilience4j Retry；
- Circuit Breaker；
- 对网络错误、429、5xx 等瞬时故障重试；
- AI 调用日志与 Token 计量。

解析错误和普通 4xx 不会被当成瞬时故障无限重试。

### 3.7 报告落库

审查成功后会保存：

- `review_report`：总体风险、摘要、问题数量、原始模型响应；
- `review_issue`：严重程度、类别、文件位置、描述、影响、证据、建议和置信度。

前端按照 HIGH、MEDIUM、LOW、NONE 的顺序展示问题。

## 4. RabbitMQ 当前实现

经典审查模式包含：

- `code.review.task.queue`：工作队列；
- `code.review.delay.queue`：延迟重试队列；
- `code.review.dead.queue`：最终死亡队列；
- `review.exchange`：DirectExchange。

失败后的处理流程：

```text
消费失败
→ 未超过 max-retry：应用发布 nextRetry 消息到 delay queue
→ delay queue 固定 TTL 到期
→ RabbitMQ 通过 DLX 回投 task queue
→ 再次消费
→ 超过 max-retry：任务标记 DEAD，应用主动发布到 dead queue
```

准确口径是：

> 重试使用 TTL + DLX 延迟回投；最终 dead queue 由应用层主动发布。

当前是固定延迟，不是指数退避；重试通过 catch 后发布新消息实现，不是 nack/requeue。

## 5. PR 工作流

### 5.1 手工 PR 工作流

这是当前已经可用的 PR 能力。用户可以登记：

- PR 编号；
- Provider；
- 标题和作者；
- 源分支和目标分支；
- Base SHA 和 Head SHA；
- 外部 PR ID。

登记后可以：

1. 选择 PR；
2. 选择参与审查的知识文档；
3. 基于 PR 的 Base/Head Diff 创建审查任务；
4. 查看与 PR 关联的报告；
5. 选择高危或中危问题；
6. 提交管理员动作。

动作包括：

- `APPROVE`：通过；
- `REQUEST_CHANGES`：打回修改；
- `WAIVE`：风险豁免；
- `COMMENT`：仅评论。

这套能力是在 RepoSage 内部手工登记和操作 PR，不等于 GitHub/GitLab PR 已经全部自动同步。

### 5.2 兼容的旧 GitHub webhook

旧入口：

```text
POST /api/webhooks/github
```

它可以接收 GitHub PR 事件，触发经典审查，并在配置仓库 token 和允许回写时尝试发布 GitHub PR 评论。

边界：

- 只支持 GitHub；
- 只发布 PR comment，不是完整 Check Run；
- 回写失败会被记录，但不会破坏已经成功的审查任务。

## 6. 新 GitHub/GitLab SCM 控制面

新入口：

```text
POST /api/webhooks/scm/github
POST /api/webhooks/scm/gitlab
```

### 6.1 已实现能力

#### 安装级配置

`scm_installation` 保存：

- Provider；
- 安装标识；
- 绑定的项目和仓库；
- 加密 webhook secret；
- 加密 API credential；
- API Base URL。

#### Webhook 校验

- GitHub 使用 HMAC-SHA256；
- GitLab 使用 webhook token；
- 比较过程使用 constant-time 方式；
- 密钥来自服务端安装记录，不从 webhook 载荷接收。

#### Delivery 去重

`scm_webhook_delivery` 通过 provider + delivery ID 唯一约束避免重复处理，并保存 payload hash、有限预览、状态和关联 run。

#### 事件规范化

GitHub PR 和 GitLab MR 会被转换为统一的 `NormalizedPullRequestEvent`，使后续控制面不依赖具体 Provider 的 JSON 结构。

#### AgentRun 创建

`WebhookAgentRunService` 使用以下形式的触发键：

```text
provider:installation:pr:<number>:<headSha>
```

相同事件重复到达时返回既有 Run；同一 PR 出现新 Head SHA 时，旧的非终态 Run 会被标记为 `CANCELED / SUPERSEDED`。

AgentRun 创建与 PENDING Outbox 事件写入在同一个数据库事务中完成，Webhook 可以在持久化后返回 HTTP 202。

### 6.2 当前尚未贯通

当前链路停在：

```text
Webhook
→ 验签和去重
→ NormalizedPullRequestEvent
→ AgentRun(RECEIVED)
→ PENDING Outbox 入库
```

尚未自动继续：

```text
Outbox dispatcher
→ RabbitMQ Agent step
→ AgentStepConsumer
→ SandboxToolGateway
→ sandbox-runner
→ Findings/报告
→ GitHub/GitLab publisher
```

具体缺口：

- 没有完整的 Outbox dispatcher；
- `AgentStepConsumer` 仍是执行骨架；
- `AgentRecoveryService` 尚未扫描和恢复中断任务；
- 后端默认使用 `NoopSandboxToolGateway`；
- publisher 尚未由新 Agent 流程自动调用。

因此，新 SCM 端点当前应描述为“安全接入和 AgentRun 控制面入口已实现”，不能描述为“Webhook 自动审查回写已经端到端完成”。

## 7. Agent 控制面

### 7.1 AgentRun 与 AgentStep

数据库已经持久化：

- Run 的项目、仓库、PR、Head/Base SHA；
- 当前状态和步骤序号；
- 是否请求取消；
- 失败类型和信息；
- 开始、完成、创建、更新时间；
- 乐观锁版本；
- 每个 Step 的序号、状态、输入输出和执行时间。

### 7.2 状态机

主要状态路径包括：

```text
RECEIVED
→ PREPARING_REPOSITORY
→ ANALYZING_CHANGE
→ PLANNING
→ EXECUTING_TOOLS
→ RETRIEVING_CONTEXT
→ VERIFYING_FINDINGS
→ GENERATING_PATCH
→ VALIDATING_PATCH
→ WAITING_APPROVAL
→ PUBLISHING_RESULT
→ COMPLETED
```

另有：

- `RETRY_WAIT`；
- `FAILED`；
- `CANCELED`；
- `TIMED_OUT`。

状态机允许部分分支跳过 Patch 或审批阶段，并拒绝未声明的非法转换。

### 7.3 预算守卫

Agent 预算结构可以限制：

- 最大运行时间；
- 工具调用次数；
- 模型调用次数；
- 输入 Token；
- 输出 Token；
- 成本。

目前预算、状态机、计划和工具约束类已经存在，但由于步骤执行器尚未完成，这些约束还没有形成完整的自动 Agent 运行链路。

### 7.4 Timeline 与 SSE

持久化 Timeline 查询：

```text
GET /api/agent-runs/{runId}
```

会返回 AgentRun 和按顺序排列的 AgentStep。

SSE 入口：

```text
GET /api/agent-runs/{runId}/events
```

当前只创建和保存 `SseEmitter`，尚未形成完整的 Run 级事件广播、断线回放和 `Last-Event-ID` 语义。因此当前应以数据库 Timeline 查询为主要事实来源。

## 8. sandbox-runner

`sandbox-runner` 是独立 Maven 模块，没有入站 HTTP 端口，设计上只消费专用 RabbitMQ 作业。

### 8.1 已实现的安全能力

#### 作业签名与防重放

- HMAC-SHA256 签名；
- canonical JSON；
- 过期时间校验；
- nonce 防重放；
- 后端和 runner 有 golden vector 测试保证签名兼容。

#### 命令白名单

当前只允许：

```text
git.diff
git.file
code.search
```

不会直接执行消息里携带的任意 shell 命令。

#### 容器限制

容器策略包括：

- `--network none`；
- 只读根文件系统；
- 非 root 用户；
- `cap-drop ALL`；
- `no-new-privileges`；
- PID、内存和 CPU 限制；
- timeout；
- tmpfs；
- 仓库只读挂载。

#### 文件和网络安全

模块还包括：

- 工作区路径围栏；
- 有界文件读取和代码搜索；
- Zip Slip 防护；
- 符号链接逃逸检查；
- Zip Bomb 限制；
- SSRF 地址校验；
- 拒绝环回、私网、链路本地和云元数据地址。

### 8.2 当前接线状态

runner 本身和沙箱协议已经实现，但 backend 默认的 `NoopSandboxToolGateway` 会返回 sandbox dispatch 未配置。因此目前不能说 Agent 已经能够自动通过 sandbox-runner 读取仓库。

准确状态是：

> runner 模块可以独立测试，backend → MQ → runner → 结果回收的真实网关仍待实现。

### 8.3 安全边界

Docker Compose 中 runner 通过 docker-socket-proxy 访问受限 Docker API，原始 Docker socket 不直接进入 runner；被分析仓库的临时容器也不会获得 Docker socket。

但单机 Compose 只适合受控演示，不是针对恶意多租户的强隔离方案。更强的隔离仍需要虚拟机、Kata Containers、Firecracker 等边界。

## 9. 结果发布器

项目已经实现：

### GitHub

- PR comment；
- Check Run。

### GitLab

- MR note；
- Commit status。

如果发布内容暴露生成的补丁，`ReviewPublication` 必须带人工批准状态，否则 publisher 会拒绝发布。

当前 publisher 类和测试已经存在，但尚未接入新的 SCM Agent 自动完成链路。

## 10. 安全、可观测与工程护栏

### 10.1 安全

当前包括：

- Token/Cookie 鉴权；
- 无公开注册；
- Git token AES-GCM 加密；
- SCM credential 和 webhook secret AES-GCM 加密；
- Webhook HMAC/token 校验；
- Git 输入校验；
- 沙箱作业签名和防重放；
- 生产环境弱密钥与占位配置检查。

### 10.2 Trace ID

每个请求会生成或透传：

```text
X-Trace-Id
```

Trace ID 写入 MDC 和响应头。前端 API Client 会把错误响应中的 Trace ID 拼入错误提示，方便关联后端日志。

### 10.3 限流

`/api/**` 使用固定窗口限流：

- 登录用户按 user；
- 其他请求按 IP；
- 超限返回 429；
- 响应包含 `Retry-After`。

当前实现是单实例内存计数，不是 Redis 或其他分布式全局限流。多实例部署时，各实例分别计数。

### 10.4 AI 调用日志

`ai_call_log` 记录：

- 请求类型；
- Provider 和模型；
- Prompt/响应字符数；
- Prompt Token；
- Completion Token；
- Total Token；
- 调用耗时；
- 成功/失败状态；

## 14. 当前最适合的演示路径

如果用于课程答辩、面试或项目展示，建议演示已经完成的经典链路：

1. 使用显式配置的种子账号登录；
2. 创建一个项目；
3. 绑定 `demo-repos/mall-order-service`；
4. 上传 `order-flow.md`、`security-policy.md` 等知识文档；
5. 查看 Commit 和 Diff；
6. 先使用 Mock AI 触发审查，证明无外部 Key 也能跑通；
7. 再切换 OpenAI 兼容模型，展示真实模型报告；
8. 查看报告中的文件位置、证据和修改建议；
9. 标记真实问题或误报；
10. 登记 PR，关联报告并提交打回/通过动作；
11. 查看 AI 调用日志、Token 用量和 Trace ID。

对于 Agent/SCM/沙箱部分，建议按工程演进方式展示：

- 展示 GitHub/GitLab webhook 验签和幂等触发；
- 展示 AgentRun 状态机、预算和 Outbox 数据结构；
- 展示 sandbox-runner 的签名、防重放与容器限制测试；
- 主动说明自动步骤执行和结果发布仍待接线。

这种表述既能体现项目的工程深度，也不会把尚未贯通的能力夸大为已经生产可用。
