# RepoSage 项目详细介绍

> 本文是 RepoSage 的端到端全景介绍：它是什么、解决什么问题、如何架构、审查引擎怎么工作、两条核心数据流、各模块职责、关键工程取舍与演进路线。想快速上手运行见根目录 [`README.md`](../README.md)；SCM/沙箱安全细节见 [`13_SCM接入与沙箱运维.md`](13_SCM接入与沙箱运维.md)。

---

## 1. 一句话定位

**RepoSage 是一个智能代码审查平台**：以 Git Commit / Pull Request 的 Diff 为输入，提供内置规则审查、可选轻量模型风险信号和项目知识库（RAG）上下文，通过 Mock 或 OpenAI 兼容模型生成带证据链的结构化审查报告；并在此之上演进为一个**可恢复、可观测、有预算约束的 PR 守门 Agent**。

它有意做成一个「**AI 应用 + 后端工程**」的写实范例：经典审查链路既能接真实大模型，也能在无 Key、无 PostgreSQL/RabbitMQ 的本地环境下演示；SCM、Agent 与沙箱的新自动化链路则明确区分“组件已实现”和“端到端已贯通”。

### 当前实现状态

- **已经端到端可运行**：仓库绑定与 Git Diff、幂等审查任务、inline/RabbitMQ 经典审查、可选轻量模型、RAG、Mock/OpenAI 兼容审查、报告落库与前端展示、手工 PR 工作流。
- **兼容链路可用**：旧 GitHub webhook 可触发经典审查，并在满足配置条件时回写 GitHub PR 评论。
- **新控制面已实现基础**：GitHub/GitLab webhook 验签、delivery 去重、事件规范化、AgentRun 创建，Agent 状态机/预算/Outbox 数据结构，独立 sandbox-runner，以及 GitHub/GitLab publisher 类。
- **自动闭环仍待贯通**：当前没有 Outbox dispatcher；`AgentStepConsumer` 与 `AgentRecoveryService` 尚未执行真实调度/恢复；后端默认使用 `NoopSandboxToolGateway`；新 SCM 事件还不会自动一路推进到沙箱执行和结果发布；SSE 目前是通道骨架。

---

## 2. 解决什么问题

传统代码审查工具（规则扫描 / linter）只懂通用模式，不懂**你这个项目的业务规则**——它不知道「下单前必须校验库存」「越权访问要走统一鉴权切面」「这张表的金额字段禁止用 float」。而直接把 Diff 丢给大模型，又常常泛泛而谈、缺少依据、无法复现。

RepoSage 的核心主张是**让审查结合项目自身上下文，并给出证据**：

- 把项目的业务规则、接口规范、库表结构、历史 Bug、安全规范作为**知识库**上传；
- 审查时把这些上下文注入 Prompt，让大模型的每条问题**尽量引用知识库中的具体依据**；
- Mock 模式用**规则审查**直接生成本地演示报告；启用真实模型时，可再加入**轻量分类模型**的风险预判作为辅助上下文。

结果是一份结构化 JSON 报告：每个问题带**严重程度、类别、文件定位、修复建议、证据来源**，可被前端展示、可被 PR 工作流消费、可回写到 PR/MR。

## 4. 系统架构

RepoSage 采用**控制面 / 执行面分离**的结构：后端是持有全部密钥的控制面，沙箱 runner 是无入站端口、被信任的执行面。

```text
                          ┌─────────────── 控制面（持有全部密钥）───────────────┐
浏览器                     │                                                     │
  │                       │   Spring Boot 后端 :8080                            │
  ▼                       │     ├─ 审查引擎（规则 + 模型 + RAG + 大模型）        │
Nginx :80 ──► Vue 前端 ───┼──►  ├─ Agent 基础（状态机 / 预算 / Outbox 数据）       │
                          │     ├─ SCM 控制面（验签 / 去重 / 规范化 / publisher）   │
GitHub / GitLab ─webhook──┼──►  └─ 依赖：                                       │
                          │          ├─ PostgreSQL（业务数据，生产可启用 pgvector）
                          │          ├─ RabbitMQ（经典异步审查）
                          │          ├─ FastAPI 模型服务 :8000（轻量风险分类，可选）
                          │          ├─ 大模型 API（OpenAI 兼容，如 MiMo，可选）
                          │          └─ Git 仓库 / 本地演示仓库（git CLI clone & diff）
                          └───────────────────────┬─────────────────────────────┘
                                                  ┊ [待贯通] Outbox dispatcher /
                                                  ┊ Agent step / SandboxToolGateway
                          ┌───────────────────────▼─────────────── 执行面（受信）──┐
                          │   sandbox-runner（模块已实现，无入站 HTTP）             │
                          │     └─ DockerSandboxExecutor ──► docker-socket-proxy   │
                          │             └─ docker run（--network none 受限临时容器）│
                          └───────────────────────────────────────────────────────┘
```

**各进程职责：**

| 进程 / 服务 | 语言 / 框架 | 职责 |
| --- | --- | --- |
| 后端 backend | Java 17 / Spring Boot 3.5 | 审查引擎、Agent 控制面、SCM 控制面、REST API、持有全部密钥 |
| 沙箱 sandbox-runner | Java / Spring Boot（无 Web 端口） | 签名作业协议、受限 Docker 和只读仓库工具已实现；后端真实派发待接入 |
| 模型服务 model-service | Python / FastAPI | 轻量风险分类（TF-IDF + 逻辑回归），HTTP 调用，可选 |
| 前端 frontend | Vue 3 / Vite | 单页应用，登录 / 项目 / 审查报告 / 日志 / PR 工作流 |
| docker-socket-proxy | Tecnativa | 过滤后的 Docker API，原始 socket 不进 runner |
| PostgreSQL | pg16 + pgvector | 业务数据；生产可启用向量列 |
| RabbitMQ | 3.13 | 经典异步审查已接入；Agent / 沙箱消息链路仍在贯通。Outbox 当前是数据库表，不是已工作的 MQ 通道 |
| Nginx | — | 反向代理，统一入口 |

> **关键口径**：本项目**不使用 Redis**；Git 操作走 **git CLI**（非 JGit）；大模型走 **OpenAI 兼容 `RestClient` 直连**（非 Spring AI）。

## 5. 审查引擎：规则审查与上下文增强

RepoSage 提供两条互补路径：Mock 模式由内置关键词/模式规则直接生成结构化报告；真实模型模式则把可选轻量模型风险信号与 RAG 项目上下文拼进 Prompt，再让 OpenAI 兼容模型结合原始 Diff 生成结论。当前规则实现是面向演示的模式匹配，并非 AST/CFG 级 SAST 引擎。

```text
          ┌───────────────┐
Commit ──►│  git CLI       │──► 结构化 Diff（可按文件分片）
Diff      └───────────────┘
                 │
       ┌─────────┴──────────────────────────┐
       ▼                                    ▼
Mock 模式                              真实模型模式
关键词 / 模式规则                     ├─ 轻量分类模型（可选）
直接生成报告                          ├─ 知识库上下文（RAG）
                                      └─ 原始 Diff
                                              │
                                              ▼
                                    OpenAI 兼容模型 + JSON 约束
       │                                      │
       └──────────────────┬───────────────────┘
                          ▼
          结构化报告（风险等级 / 问题 / 证据 / 建议）
```

**① Mock 规则审查**——纯 Java 关键词/模式匹配，识别越权、SQL 注入、空指针、业务规则破坏等常见风险，并直接生成结构化结果。它不依赖任何外部服务，主要用于本地演示与兜底验证。

**② 轻量分类模型**——独立的 FastAPI 服务，模型是 **scikit-learn 的 TF-IDF + 逻辑回归**（不是深度学习）。对 Diff 做风险预判，结果经 `toPromptContext()` 拼进真实模型 Prompt。工程亮点在于**韧性设计**：
- 模型加载失败自动回退规则匹配（结果标注 `trained-model` / `fallback-rules`）；
- 支持 `/model/reload` 热重载；
- Java 端调用失败返回 `Optional.empty()` 优雅降级，不拖垮主审查流程。

> 训练集是 demo 级（`data/risk_samples.csv`，约 28 条样本、6 类：AUTH_RISK / SQL_INJECTION / NULL_POINTER / BUSINESS_RULE_RISK / TRANSACTION_RISK / PERFORMANCE_RISK）。它的价值是**跑通「自训练模型 + 大模型协作」的链路**，而非追求分类精度。

**③ 知识库检索（RAG）**——把项目上下文喂给大模型，两种模式：

| 模式 | 触发 | 机制 | 是否需要 embedding |
| --- | --- | --- | --- |
| 全量注入（小知识库推荐） | `RAG_FULL_CONTEXT=true` | 把项目知识库文档拼进 Prompt（上限 `RAG_MAX_CONTEXT_CHARS`） | 不需要 |
| 向量检索（应用默认） | `RAG_FULL_CONTEXT=false` | `memory`（内存余弦）或 `pgvector`（数据库向量），取 Top-K 片段 | mock 可演示；高质量语义召回需真实 embedding |

> 选型说明：应用默认值是 `RAG_FULL_CONTEXT=false`；`deploy/.env.example` 为受控演示显式启用了全量注入。对只提供对话接口、没有 embedding API 的模型（如 MiMo）或小型知识库，可显式使用全量注入。pgvector 模式已实现、可切换，但当前是**精确最近邻**，**未建 HNSW/IVFFlat 近似索引**。

**大 Diff 分片**：当改动超过单次调用预算（`REVIEW_MAX_DIFF_CHARS`）时，`DiffSplitter` 按 `diff --git` 边界拆分文件、按预算打包成批，`ReviewProcessor` 逐批调用大模型，再合并结果（问题合并、风险取最高、Token 求和、summary 标注「分片审查」）。单片走原路径不变。这避免了「整体 Diff 被模型静默截断、后半段代码根本没被看」的隐患。

## 6. 两条核心数据流

### 6.1 手动 / 批量审查流

用户在前端主动发起的经典流程：

```text
登录 → 建项目 → 绑仓库 → 传知识库 → 选 commit → 触发审查任务
                                                     │
                             ┌───────────────────────┘
                             ▼
        git CLI clone & diff  →  (可选)分片  →  模型风险信号 + RAG 上下文
                             ▼
                   Mock 规则审查或真实模型生成 JSON  →  落库 report / issue
                             ▼
                    前端展示报告  →  人工反馈（确认/误报/备注）
```

- **同步 / 异步开关**：`REVIEW_INLINE=true` 时审查在请求线程内同步执行（免装 MQ，适合本地）；`false` 时任务投递 RabbitMQ 异步消费。
- **幂等**：创建阶段按项目、仓库、head/base、分支查找既有任务，并由数据库唯一约束兜底；消费阶段遇到终态任务会直接返回。

### 6.2 PR 守门 Agent 流

由 SCM 事件驱动的 PR 守门流程采用「控制面 / 执行面分离」设计，但当前需要拆成**已发生的链路**与**待贯通的目标链路**。

当前已经实现并可由 webhook 请求触发：

```text
GitHub/GitLab PR/MR 事件
   │  POST /api/webhooks/scm/{github,gitlab}
   ▼
① 按 provider 规则校验 HMAC / token，并使用 constant-time 比较
   ▼
② 根据载荷中的安装身份查 scm_installation，再使用服务端保存的安装级密钥验签
   ▼
③ 落 scm_webhook_delivery，以 provider + delivery_id 唯一键去重
   ▼
④ 规范化为 NormalizedPullRequestEvent
   ▼
⑤ WebhookAgentRunService 按 provider:install:pr:<N>:<headSha> 创建 AgentRun(RECEIVED)
   │  新 head SHA 会把同 PR 旧活跃 run 置为 CANCELED（SUPERSEDED）
   ▼
⑥ AgentRun 与 PENDING Outbox 事件在同一数据库事务中提交，HTTP 返回 202
```

目标链路已经有协议、实体与独立组件，但尚未自动连接：

```text
[PENDING Outbox]
   ┊ 缺少 dispatcher
   ▼
[AgentStepConsumer 执行状态机 / 预算 / 计划]
   ┊ 当前 consumer 仍是空壳
   ▼
[SandboxToolGateway → sandbox.job.queue → sandbox-runner]
   ┊ backend 默认 NoopSandboxToolGateway，不会真实派发
   ▼
[汇总结果 → GitHub/GitLab publisher]
   ┊ publisher 类已实现，但新 Agent 流程尚未自动调用
```

因此，当前可以准确描述为“SCM 入口、Agent 控制面数据结构、runner 和 publisher 组件已实现”，不能描述为“新 webhook 已自动完成沙箱审查与结果回写”。

### 7.1 后端 backend（19 个包，约 160 个类）

| `auth` | 登录 / me / logout，种子管理员（`AuthSeedRunner`，**无公开注册**），Token + Cookie |

| `repo` | Git 仓库绑定、commit 列表、diff 获取（git CLI） |

| `knowledge` | 知识库文档上传、分块、检索入口 |

| `sandbox` | 后端侧沙箱作业协议与签名类型；默认 `NoopSandboxToolGateway` 明确表示尚未配置真实派发 |

| `common` | `ApiResponse`、异常、`CryptoService`（AES-GCM）、`CurrentUserProvider`、`TraceIdFilter`、`RateLimitFilter` |
| `config` | `SecurityConfig`、健康探活、Flyway/迁移配置 |

### 7.2 沙箱 sandbox-runner（独立 Maven 模块，约 20 个类）

无入站 HTTP 端口（`web-application-type=none`），只 `@RabbitListener` 消费 `sandbox.job.queue`。核心类：

| 类 | 职责 |
| --- | --- |
| `SandboxJobSigner` | HMAC-SHA256 over 手写 canonical JSON，与后端**逐字一致**（golden 向量测试锁定跨模块兼容） |
| `SandboxReplayGuard` | 按 nonce 去重防重放 |
| `ContainerPolicy` | 生成加固的 `docker run` 参数：`--network none` / 只读根 / 非 root(65534) / `cap-drop ALL` / 资源限额 / tmpfs；命令白名单只放 `git.diff` `git.file` `code.search`；路径围栏 |
| `DockerSandboxExecutor` | 经 `ContainerRuntime` 启动/清理容器（幂等 kill+rm） |
| `DependencyPreparationPolicy` / `DependencyCacheManager` | 依赖缓存确定性键（maven/gradle/pip/npm/pnpm/yarn），准备作业独立白名单、无密钥，缺失返回 `ENVIRONMENT_INCOMPLETE` |
| `SafeArchiveExtractor` | 解压拒绝 `..` / 绝对路径 / 逃逸符号链接 / zip bomb |
| `RemoteResourceGuard` | 归档/子模块 URL 仅允许 https 公网地址，拒环回/私网/`169.254.169.254` 云元数据（SSRF 防护） |
| `RepositoryReadTools` | 路径围栏内的有界文件读取与代码搜索（带 `truncated` 元数据） |

### 7.3 模型服务 model-service（Python / FastAPI）

独立进程（端口 8000），`scikit-learn` TF-IDF + 逻辑回归。接口：`/predict`（风险预判）、`/model/status`、`/model/reload`（热重载）和 `/health`。模型不存在或预测异常时回退规则结果；后端调用失败则跳过该辅助信号。

### 7.4 前端 frontend（Vue 3 / Vite）

单页应用（`App.vue` + `api/client.js`）。API client **捕获响应头 `X-Trace-Id` 并拼进错误提示**，方便把前端报错和后端日志对齐；AI 调用日志展示 prompt / completion / total tokens。

## 8. 数据模型

生产 schema 由 **Flyway** 迁移管理，21 张表分布在 6 个版本，演进脉络清晰：

## 9. 关键工程设计与取舍

这一节如实记录设计决策与已知局限——**写实、不夸大**。

### 9.1 大模型接入
- 用 `RestClient` 直连 OpenAI 兼容 `/v1/chat/completions`，**没用 Spring AI**（依赖更少、可控性更强）。
- 接入 **Resilience4j 重试 + 熔断**，但**仅对瞬时故障**（网络超时 / 5xx / 429，抽象成 `AiCallTransientException`）重试；解析错误 / 4xx 不重试，避免放大无效调用。
- 每次调用落 `ai_call_log`：类型、模型、耗时、输入输出长度、**prompt/completion/total tokens**、状态、错误；并经 Micrometer 暴露 `reposage.ai.review` timer + `reposage.ai.tokens` counter 到 Prometheus。

### 9.2 消息队列（RabbitMQ）——实际实现
- 经典审查有工作队列、delay queue 和最终 dead queue；消息与队列均按持久化方式声明。
- 消费失败且未达到最大次数时，应用把带新 `retryCount` 的消息发布到 delay queue。
- delay queue 配置固定 `x-message-ttl`、`x-dead-letter-exchange` 和回投工作队列的 routing key；TTL 到期后由 RabbitMQ DLX 自动路由回工作队列。
- 达到最大重试次数后，应用调用 `publishDead()` 主动投递到最终 dead queue。因此准确口径是“**TTL + DLX 延迟回投，最终 dead queue 应用层发布**”。
- 当前是固定延迟，不是指数退避；重试仍采用 catch 后发布新消息，而非 nack/requeue。
- `REVIEW_INLINE` 提供同步/异步开关，任务创建唯一约束与终态检查共同承担幂等保护。

### 9.3 Agent 控制面
- **状态机**：`AgentStateMachine` 明确定义主路径、重试路径和终态转换，非法转换直接拒绝。
- **预算守卫**：时间 / 工具调用 / 模型调用 / 输入输出 Token / 成本等维度可在执行前检查。
- **事务 Outbox**：AgentRun 创建可与 Outbox 事件插入在同一数据库事务中提交，解决“业务状态和待派发意图同时持久化”的问题；但当前缺少 dispatcher，因此不能宣称数据库事件已可靠发布到 RabbitMQ。
- **执行与恢复边界**：`AgentStepConsumer` 尚未执行真实步骤，`AgentRecoveryService` 也仅保留恢复结构和设计意图，未完成扫描、修复和重新发布。
- **计划校验**：已有计划 Schema、工具白名单和审批顺序检查，为后续模型驱动工具调用提供约束。

### 9.4 SCM 与沙箱安全边界（不可妥协）
1. 在 JSON 规范化之前，针对**原始请求字节**验签（常时比较）。
2. 先从载荷解析身份，再据身份选密钥；**绝不**从载荷字段接受密钥或 provider 主机。
3. SCM 凭据 / webhook secret 以 AES-GCM 加密入库，不从 webhook 载荷接收，也不在普通读取接口中回显明文。
4. 沙箱容器 `--network none`、只读根、非 root、`cap-drop ALL`、`no-new-privileges`、资源限额；**命令白名单**，消息里的原始命令串一律拒绝。
5. 依赖准备（有网、独立白名单、无密钥）与不可信测试（无网）是**分离**的作业。
6. 被分析的仓库容器**永不**获得 Docker socket；runner 只经过滤后的 socket 代理访问 Docker。
7. 回写补丁内容**需人工审批**，否则拒发。

### 9.5 已知局限（如实）

**执行闭环**
- `AgentStepConsumer` 尚未执行真实 Agent 步骤，`AgentRecoveryService` 尚未完成启动恢复。
- Outbox 只有数据模型与事务内写入，缺少 dispatcher；新 SCM 事件不会自动推进到 RabbitMQ Agent 流程。
- backend 默认 `NoopSandboxToolGateway`，因此尚不会真实派发 sandbox-runner。
- GitHub/GitLab publisher 类已经实现，但尚未由新 Agent 流程自动调用；兼容的旧 PR 评论链路仅支持 GitHub。
- Agent SSE 当前只建立 emitter 通道，没有形成完整事件广播、断线回放与 `Last-Event-ID` 语义。

**数据与部署**
- pgvector 默认未启用，且未建 ANN 索引（当前精确最近邻）；大数据量需上 HNSW/IVFFlat。
- 轻量模型是 demo 级小样本分类器，不追求生产分类精度。
- 接口限流是单实例内存固定窗口，多实例部署时不能提供全局配额。
- 单机 Docker Compose 沙箱仅用于受控演示，不是面向恶意多租户的强隔离方案。

**测试与规模**
- 当前 GitHub Actions 只运行 backend 与 frontend；sandbox-runner 和 model-service 尚未纳入 CI。
- 前端测试是轻量 smoke 保障，不是完整 UI/E2E 测试。
- 项目尚未做系统压测，不提供 P95/QPS 等性能数字。

## 12. 技术栈与运行

核心技术栈包括 Java 17 / Spring Boot 3.5、Vue 3 / Vite、PostgreSQL 16 + pgvector、RabbitMQ、FastAPI + scikit-learn，以及独立的 `sandbox-runner` 与 Docker Compose 演示环境。

本地开发默认使用 H2、Mock AI 和 inline 审查，因此经典审查不要求 PostgreSQL、RabbitMQ 或大模型 Key；但应用默认不会创建管理员账号，需显式配置 `SEED_ADMIN_USERNAME` 和 `SEED_ADMIN_PASSWORD`。`deploy/.env.example` 与冒烟脚本中的凭据只是示例或脚本参数，不是应用默认值。

启动命令、真实模型接入、完整环境变量、Docker 部署和测试入口统一见根目录 [`README.md`](../README.md)，避免在两份文档中维护两套运行手册。
